### The false alarms

Six findings matched nothing in the cases. One was a real issue the case already
listed under another rule (a provider refund that does not fit the payment is never
booked); IDEM-10 is now accepted next to PSP-10 there. The other five pointed at gaps
in the fixtures, not at the tool:

- three commission cases add `paid_at` with no backfill, so payments made before the
  deploy drop out of the commission. The migrations now say the partner program starts
  with this release, so no earlier payment has a partner;
- in `clean-psp-cardhub-ipn` a success that arrives after a decline is dropped with no
  trace. The controller now states CardHub's contract: one card attempt per hosted
  order, a retry is a new order.

A targeted rerun after these fixes found three more gaps of the same kind (`paid_at`
written in the app time zone, commission rounded down with no stated rule, a refund
mismatch kept only in a log line in a clean case) and they were fixed too. The last
rerun of the six touched cases, three runs each, had no false alarm and missed no bug.

## Changes made during this eval

Before the full run (commits 14f9a47 to bc0259c): IDEM-1 covers an API endpoint that
moves money with no idempotency key while its siblings take one; IDEM-5 does not report
an action a person starts by hand; PSP-3 does not report a handler behind a provider
setting that sends one event type. Older cases accept findings under the new rules
where the finding is the same bug.

After it: the verifier treats a rule stated in a repository doc or in a named constant
like a comment at the code, and reads the module's notes (README, CLAUDE.md, `docs/`)
before it calls a behaviour unintended. The last synthetic rerun used this verifier.
